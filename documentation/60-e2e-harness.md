# E2E suite — uscode-mcp's half of the mcp-e2e contract

The harness is a standalone project, `mcp-e2e` (R11). Its mechanics — manifest loading, cells, drivers, checks engine, run artifacts, the four check outcomes — are `SUITE-AUTHORING.md`'s to define (with the harness repo's own spec normative on conflict). This file holds only what is uscode-mcp-specific: the suite.

The suite is spec-session property: the manifest (`e2e-manifest.json`, loaded verbatim by the harness — no copies), the groundings behind it, and the scored findings from runs. Two runs are comparable only on matching manifest hashes or an explained delta.

## Binding suite rules

**Preregistration-of-scoring** (inherited, restated because it binds this directory): `pass`/`fail` are pinned before a run and never edited after seeing a result they would score; criteria change only between runs with rationale committed. `watch` fields pin attention, not scoring, and may be edited freely.

**Audience.** The asker sees only the answer. Under the Claude Code drivers a person at the terminal can also watch tool results scroll by; under the loop driver nothing but `answer.txt` reaches them. A criterion that accepts "how to continue" therefore means a continuation the asker can execute — a URL, an offer the consumer will carry out on request, a summary — never a tool name or a `start_char`. Ruled 2026-09-18 from F7 (O51c): all 21 loop-driver C1 answers relayed the server's `start_char` continuation to the asker verbatim, and every one passed the version-1 criteria.

**Cap-cut answers.** An answer that ends mid-paste with completion tokens at the cell's `max_tokens` is a knob artifact, not a model choice (O51b: three of ten pinned C1 rows, `completion_tokens` 4,171–4,176 against a 4096 cap, no finish reason recorded anywhere in the row). Such a row is set aside — reported with its token counts, not scored — on any clause about what the answer claims versus what it delivers. Once the harness records the finish reason on the wire (S13), only rows whose finish reason is the model's own stop are scored on those clauses; the token-count inference is the interim instrument and is named as such wherever it is used.

**First-run instrument validation.** The Layer-1 checks were authored against the measured envelope (O28) plus one assumption — that the harness roots the tool response at `/response`, putting the structured payload at `/response/structuredContent/...`. Before any check outcome is scored: `mcp-e2e validate` must accept the manifest, and one smoke cell must show every check non-vacuous on a run that exercised its surface. A vacuous check is an instrument question, never a pass — if the pointer root is wrong, every check will be vacuous at once, which is the tripwire working.

**Outcome vocabulary.** Measured members are pinned: `success`, `not_found`, `ambiguous`, `out_of_scope_private_law` (O28) and `appendix_redirect` (O29, live trace). `out_of_scope_collection` (R17) is measured — served shape `offending_clause`, `collection`, `message`, optional `suggested_tool`, in live traces (O57a/b) — and joins the pinned vocabulary; no manifest check binds it yet, and none is added until the loop manifest's pending re-sync to version 3 is done (one version bump at a time). Implementation-claimed members (upstream-failure, rate-limited, `format_not_available`) are not bound by any check until measured — a check written against a guessed name false-fails legitimate outcomes. When a run's trace exhibits a new outcome shape, measure it there (the trace is the measurement) and extend the checks in the same commit as the observation.

**Attribution discipline.** Fabrication and answered-from-priors clauses (in A2, C2, D3) are scorable only in the `isolation` cell, where trace scope equals tool surface — SUITE-AUTHORING's rule, applied to the three prompts that need it. In `floor`/`ceiling` those clauses are watch items, never scores.

**Edition staleness.** Groundings marked edition-dependent are pinned to the 2024 edition (`currentthrough` 2025-01-06, O15). When GovInfo publishes a newer annual edition, those groundings are stale: re-measure before scoring any run. The harness's per-run upstream identifiers make staleness detectable after the fact; the fixture `content_hash_sha256_16` values (O28) make it checkable by re-fetch.

## What Layer 1 asserts, and why

Each check in the manifest maps to a `40-tools.md` contract: outcome discriminator present (three-outcomes taxonomy); zero-hits echo the upstream query; normalization strips disclosed (the diagnosability the maintainer named in Q7b); provenance blocks complete, `currentthrough` included (staleness disclosure, load-bearing after R1); truncation markers on every window (measured live against the 3.59M-char NDAA, O28); disambiguation true totals; `recall_caveat` on every successful `search_public_laws` response (O21's gap must not be laundered); private-law scope outcome distinct from not-found (R6). Rate-limit behavior stays unit-test territory (untriggerable live, O13).

## Layer 2 and classification

Layer 2 scoring is the human's and/or this session's, from artifacts, never summaries. Every failure is classified before filing — consumer-behavior finding vs tool defect vs instrument defect — and no finding of any class is recorded from a defective instrument; a zero-trace run is BROKEN, never abstention. Scored findings are committed here, each citing the run artifacts it was scored from.

**Harness request — an interview mode on a scored row (requested 2026-09-24; maintainer-approved the same day; not built).** What this suite wants: a way to resume a scored loop row's session *after* its scored turn and put one or more operator-written follow-up questions to the same model in the same context — the tool results it saw, the answer it gave — and record the exchange. Why: the trace shows what a consumer did and never why. Three rows this week each needed one question no artifact can answer — the C4 row that asked `max_chars: 0`, was refused, and never retried ("why did you stop?"); any E26 after-arm row ("what did the caveat tell you to do, and who is the person asking?", the residual behind Q22/R25); the A5 rows that read an `ambiguous` response listing two rules and presented one as unique ("why did you not mention the second?", F10's next step). S11 and S18 were this instrument run by hand on capable consumers, and both produced findings that measured real (WO-12); the loop driver can run it on the floor. Shape this suite would consume: (1) `mcp-e2e interview --row <row dir> --ask <text>` (or a file of questions), resuming the row's recorded session with the same scaffold, pin and knobs, the tool surface still mounted, so the model can call tools while answering if it chooses; (2) it runs only on a row whose scored turn is complete and writes nothing into that row's scored artifacts — the exchange lands beside them (`interview/` under the row, with its own wire lines, session file and trace) and is marked so that nothing aggregates it; (3) the operator's questions are recorded verbatim with the answers, so a quote is traceable to its question; (4) cost and provider are recorded as for any turn. What it is not: it is not scored, never pools with rows, and its answers enter this spec as S-numbered claims to preregister against, never as observations — the rule that binds S18 binds this. Where it pays: failed rows in any cell, and the more capable lineage and the capability cells, whose self-reports are worth more; least on the floor model's account of how the tool felt. Not a check, not a measurement, not a Layer-1 extension.

**Harness measurement `answer_coverage` — DELIVERED as `answer-coverage@1` and declared in manifest version 5 (reference `text.content` on both text tools, floor 64; per-row in `meta.json` → `measurements.answer_coverage`, read beside `finish_reason`). The request as made follows. Requested (2026-09-18, answering the harness spec session's Q1 first-candidate question).** This suite wants it, as a per-row measurement recorded beside the run and never a check outcome. What it serves: the version-2 C1 contents clause has two halves — what the answer claims to contain (prose, the scorer's read) and what it actually reproduces from the tool result (mechanical). The mechanical half was computed by hand twice on `pinned-r09` with different results (harness session 6,769 shown / stop 6,764; this session 6,765 / 6,717 — same artifact, different fence-boundary rule, O51/S13), which is the case for a defined measure whose method is pinned like a scaffold. Shape this suite would consume: (1) reference string named by a suite-declared `tool` + RFC 6901 pointer in the manifest, reusing the checks selector vocabulary — here `/response/structuredContent/text/content` on both text tools — never the whole serialized tool message, whose JSON escaping differs from what the model emits; (2) whitespace-normalized matching with a minimum span length, because `pinned-r07` and `unpinned-r06` reformatted their pastes (O51a) and exact matching undercounts them, while short matches (citations, headings) would overcount; (3) per record: `matched_chars` (sum of matched spans), `max_offset` (the furthest reference offset any span reaches, not the end of the first span), and `share` over the reference length, offsets in the reference string's own coordinates — this suite subtracts its banner itself (R13c); (4) recorded on the same row summary as the finish reason (S13): 33% with a model stop is a model cut, 100% with a length stop is a knob cut, and without the finish reason the number is ambiguous, which is O51b. What it does not do, stated so nobody turns it into a score: it cannot read the claim, and it cannot separate paraphrase from omission — this suite will read it on prompts whose expected answer quotes (C1, C3, C4) and ignore it where the answer is a summary (Group A). It is not an answer to the harness's Q1: Q1 asks about run-scoped assertions, and this is a per-row measurement across two artifacts; it should not become the precedent for extending the Layer-1 assertion language.

## Cells and gating

Three gating cells: `floor` (Sonnet, no thinking, crowded via the harness-owned `neutral-file-triage@2` procedure — collision review attested in the manifest: statutory-law retrieval is disjoint from office notes-triage), `ceiling` (Opus, high thinking, fresh), `isolation` (the four server tools exactly, fresh — the attribution cell). The grid grows only when a question needs a new cell.

**Gating by failure class (R24, 2026-09-23).** No cell gates by identity. The three Claude Code cells (`floor`, `ceiling`, `isolation`) are ceiling/capability cells and gate the full behavioral contract: every `fail` clause of every prompt, and every check. The loop cells (`loop-floor`, `loop-isolation`, `loop-floor-deepseek`) are floor/lean-prompt cells and gate on two classes only. **Class 1, substantive correctness** — the answer states something about the law that is false or unsupported by retrieved text: A2, text attributed to a designator that does not exist (F8); A3, edition text presented as current law with no currency qualification; A4, the result set presented as complete; A5, one of two colliding granules presented as unique (the borderline case — the answer asserts an identity that is half true — placed here and flagged for the maintainer); C1, a window presented as the whole law, or a claim to have delivered or read it; C2, a misquotation or miscitation; C3, provisions asserted that are not grounded, coverage claimed without retrieval, or the law reported as not addressing the topic (F11); C4, a fabricated or unretrieved quotation, or a claim that no apology exists; D1 and D3, fabricated content; D2, fabricated content of the private law; D4, the current edition returned silently as the 2015 one, or historical text reported unavailable. **Class 2, explicit tool-contract violations** — any Layer-1 check with a per-cell outcome of `fail` in `checks-report.json`. **Class 3, measured diagnostics in the loop cells, gating only in the capability cells:** a tool-call recipe, `start_char`, field name or package id relayed to the asker (F7(ii), F9, the E17 shape); an excerpt described by the window's size and cut early with a marked cut (F7(i)); the API-host link offered beside the public one; D2's "couldn't find it" framing and D1/D3's zero-hit presented as malfunction; C4's locating by blind offsets when `find` and `structure` were available (E14's falsifier, a discoverability finding by its own terms); C1's paging attempt; wrong section numbers attached to real provisions (three gpt-oss C3 rows so far — a candidate for promotion to class 1, not promoted); invented descriptions of note contents from headings (A1, two rows). Instrument cells — `e17-akashml`, every experiment arm — never gate. The class of a clause is fixed here, not decided per row; a new failure species is assigned a class when it is first logged, and moves only by a ruling. Consequence on the record: the version-7 complete run gates red in `loop-floor` and `loop-isolation` (A2 and A5, class 1, every row) and green in `loop-floor-deepseek`. Manifest: version 8 sets `merge_gating: true` on the three loop cells with this scoping in their `notes`, and is published after E26's after-arm so that arm runs under the baseline's hash; `merge_gating` is not among the `cell_id` components (`knobs`, `setup`, `env`, `selection`, `scaffold`, `pin`, read from the version-7 rows), so version-8 rows should pool with version-7 rows — to be confirmed from the first version-8 row's `cell_id`.
