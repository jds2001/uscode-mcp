O40 — Wire-shape duplication, raised by the maintainer and measured on run 035906Z isolation/C1: `content[0].text` is byte-for-byte the JSON serialization of `structuredContent` (parses equal), so a 100,082-char window ships as a 208,372-byte response.

O40a — the same duplication re-measured 2026-09-02 at higher precision, on both records of that trace, after the maintainer asked whether the identical content is real. It is, and the relation is exact, not approximate: `content[0].text == json.dumps(structuredContent, indent=2, ensure_ascii=False)` for record 0 and record 1 alike — pinned by testing candidate serializations, since a plain `json.dumps` and an `ensure_ascii=True` form both compare unequal. So the payload appears twice per response: once raw at `structuredContent.text.content`, once inside the serialized envelope at `content[0].text`. Record 0: 100,082 payload chars, 103,040 in the serialized copy (2,958 chars of envelope), 208,372 response bytes. Record 1: 2,079 / 2,920 (841 chars of envelope), 6,026 bytes. Envelope overhead is near-constant, so duplication dominates at large payloads and the envelope dominates at small ones.

O40b — the boundary on O40's cost claim, stated because the acceptance rests on it. "Model context is 1×" is an **inference from consumer behavior**, not a measurement: consumers quote `recall_caveat`, `find` fields and offsets that exist only in the envelope copy, which shows they read the serialized copy — it does not show the host withheld the other one. The instrument cannot currently settle it: `api-surface.jsonl` records `path`, `model`, `tool_names` and `body_keys` per request, never message bodies, so no artifact in the run says how many copies of a tool result entered the request. What would settle it: capture per-request token counts (the driver already calls `/v1/messages/count_tokens`, seq 3 in this cell) or request-body sizes alongside the existing keys, then compare a large-payload cell against its response bytes. Until then the 2× is measured on wire, trace files and memory; the context multiplier is 1× by inference only.

Standard-behavior note (secondary, not a measurement): the MCP specification asks a tool returning structured content to also return functionally equivalent unstructured content for backwards compatibility, giving serialized JSON in a text block as its example. That is the documented reason this shape is not an implementation choice; it is cited as spec text, not as something measured here. This is the MCP SDK's standard dual emission for structured-output tools (compat text block + typed block), not an implementation choice. Cost profile: model context is 1× — consumers demonstrably read the JSON envelope copy (they quote `recall_caveat`, `find` fields, and offsets, which exist only in the envelope); the 2× lands on wire, trace files, and memory. The instrument depends on `structuredContent` (all Layer-1 check pointers); host visibility depends on the content block. Accepted as-is: any split that keeps the payload visible to both the model and the checks retains the duplication, and the recoverable cost is disposable trace bytes.

O41 — Two measurements prompted by S10, both on run 035906Z artifacts.

**(a) The O40a serialization pin rests entirely on the banner's punctuation — and the mechanism is not the en-dash alone.** S10 flagged that `ensure_ascii=False` is what lets the en-dash in `chars 0–99,999` survive as a literal, and that a maintainer "fixing" the dash would silently break the equality test without breaking anything real. Measured: the entire `structuredContent` of the 100k record contains exactly four non-ASCII characters — two en-dashes (`–`) and two em-dashes (`—`) — and every one of them is in the E12 banner (`[WINDOW chars 0–99,999 of 3,590,552 — truncated; …]`), counted twice because the banner is also the head of `content`. The `message` key is pure ASCII; so is the GPO payload body for this fixture. Correcting S10: replacing only the en-dash with a hyphen does NOT collapse the discrimination (`ensure_ascii=True` and `False` still differ, because the em-dash remains) — both characters would have to go ASCII. The stronger consequence S10 was reaching for: **on a non-truncated response there is no banner, hence no non-ASCII, hence `ensure_ascii=True` and `False` serialize identically and the pin cannot discriminate at all.** O40a's `ensure_ascii=False` finding is therefore established only on bannered responses of an ASCII-payload fixture; it is a fact about this response shape, not a general property of the server. Any future test asserting it must be scoped to a truncated response and must state that the banner's dashes are the load-bearing characters, or it will read as a serialization contract the server never promised.

**(b) Every C1 consumer that used the default `max_chars` abandoned the result and re-requested smaller — 2 of 2.** Call patterns across the three C1 cells (denominator: 3 cells, the full C1 set for run 035906Z): floor called with no `max_chars` (100,000 returned, 208,372 bytes) then immediately re-called the SAME offset with `max_chars: 500`; isolation did the same, retreating to `max_chars: 2000`; ceiling never touched the default — it opened at `max_chars: 3000` and then made five `find` calls at `max_chars: 200`, never exceeding ~8KB on any response.
