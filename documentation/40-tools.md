# MCP tool surface

Four tools. Small on purpose: each maps to one recipe in `30-search.md`, and everything else (summaries, alternate formats) rides along as links in responses rather than as more tools.

## Cross-cutting contracts

These bind every tool:

**Three distinct outcomes, never collapsed.** (1) Success, possibly with zero results — a zero-hit search says so explicitly and echoes the exact query sent upstream. (2) Upstream failure — HTTP status and body surfaced; a failed call must never present as "not found". (3) Rate-limited — HTTP 429 surfaced as its own outcome with `x-ratelimit-*`/`Retry-After` information passed through (limit measured at 36,000/hr, O13 — headroom is real but the contract doesn't depend on it). A 2xx whose body is not the shape the server reads — not JSON, `results` not a list of objects, a summary that is not an object, a required field of the wrong type — is outcome (2): `upstream_error` with the HTTP status, the body verbatim, and a `detail` naming what was expected and what arrived; inside `possibly_superseded` it is `not_checked` / `malformed_response`, as already specified. It must never leave the tool as an unhandled exception, because a host shows that as a generic tool failure with no status, no body and no query — a failed call that says nothing about why is one step from reading as "not found". Added 2026-09-20 from S17 finding 3, a claim about code this session cannot observe; no wrongly-typed 2xx body appears in any run artifact (O61f), so this is cheap insurance at the one place bodies are parsed, verified at unit level only, and not a licence for per-field defensive machinery.

**Provenance on every text payload.** Any response containing statutory text states: `packageId`, `granuleId` (when granule-level), edition year, the `currentthrough` date parsed from the granule HTML comment (O5, O15), `lastModified`, and three links: `pdf_link` (the upstream `download.pdfLink`, on `api.govinfo.gov`, requires the key — for the tool caller), `public_pdf_link` (`https://www.govinfo.gov/content/pkg/{package_id}/pdf/{package_id}.pdf` for a package, `…/pdf/{granule_id}.pdf` for a granule, built from the response's own identifiers and nothing else; opens without a key, O53b/c — for a person), and `details_link` (the upstream `detailsLink` verbatim, the document page, no key, O53d — the fallback that assumes no URL pattern). `details_link` is null on the citation path of `get_us_code_section`: that path resolves through a search hit and fetches no summary, and search hits carry no `detailsLink` on either collection (O54d, measured by both sessions); the null is accepted and disclosed rather than bought with a granule-summary fetch per citation lookup, because `package_id` is present on every path where `details_link` could be, so `public_pdf_link` is always built and the fallback never fires — revisit if a consumer is measured wanting the details page rather than the PDF. Corrected 2026-09-19 (O53): the contract had said "the canonical PDF link" without naming a host, the implementation took `download.pdfLink`, and WO-6 wrote that key-requiring URL into the sentence addressed to the person asking — a link they cannot open. WO-7, built at c373a2e and verified O54: every served `public_pdf_link` opened without a key, 7 of 7 across both tools, two historical editions, and an appendix granule. If `currentthrough` cannot be parsed, say so — do not omit silently. Given the backend ruling (R1), `currentthrough` is the staleness disclosure and is non-optional.

**No silent truncation.** Text responses take an optional `max_chars` (default **20000** — lowered from 100,000 on 2026-09-16 per E15/O47: a 100,082-char window was measured NOT delivered inline to the model by claude-code 2.1.236, which counted it and substituted a ~3 KB stand-in, while a 20,081-char window in the same cell was delivered inline; the default sits just under the largest window measured to arrive, and a consumer that wants more asks for it explicitly; the threshold is a host property and is re-measured when the driver changes — WO-4) and `start_char` (default 0). When the payload exceeds the window, the response states total length, the window returned, and the `start_char` to continue from. Full text is never elided without these markers. **Window arguments are checked where they can be (O61e, from S17 finding 4).** What is decidable from the arguments alone — `max_chars` ≤ 0, `start_char` < 0, a non-integer — is `invalid_argument` before any upstream request; served at 633e61c these refusals took 542–1,166 ms against 6 ms for a locally-refused control, a full lookup spent to reject an argument, and against a 36,000/hr budget (O13) that is quota a malformed loop can burn. What needs the payload is decided after it: a `start_char` greater than zero and at or past `total_chars` is `invalid_argument` carrying `total_chars` and saying that no text exists at that offset and that the document was retrieved and is not empty — never `success` with an empty window and `truncated: false`, which is what was served and which reads as an empty document. `start_char: 0` on an empty payload remains a `success`. A consumer following `next_start_char` cannot reach this case, since the last window's is null; one doing its own arithmetic can. **The markers must also live inside the text itself**: when `truncated` is true, `text.content` begins with a single bracketed banner line stating the window bounds, the true total, and the continuation `start_char` (e.g. `[WINDOW chars 0–99,999 of 3,590,552 — truncated; continue with start_char=100000]`). Ruled 2026-09-01 from finding F1 (`70-run-findings.md`): a floor consumer, given complete and correct structured truncation fields, still presented the window as the whole law — the disclosure has to sit in the stream the model actually reads, not only beside it. Preregistered as E12. Load-bearing in both collections: a section granule reached 142KB (O15) and a public law is a single multi-thousand-page package (O8). **The message must also address the audience.** When `truncated` is true, `text.message` — the in-band prose channel (R13c) — states, after the continuation, that the `start_char` continuation is for the tool caller, and that a person asking for the whole document should be given the PDF link, with the response's `public_pdf_link` written into the sentence — never `pdf_link`, which 401s without the key (O53a), and never a pointer to the field (e.g. `Continue with start_char=20000. That continuation is for you, the tool caller; if the person asking wants the whole document, give them the PDF: https://www.govinfo.gov/content/pkg/PLAW-118publ31/pdf/PLAW-118publ31.pdf`). When `public_pdf_link` cannot be built, the sentence gives `details_link`; when neither exists, it says no link is available. Ruled 2026-09-18 from F7 (`70-run-findings.md`; O51c): under the harness's loop driver, 21 of 21 C1 answers relayed the continuation to the asker verbatim, 0 of 10 pinned answers offered the PDF link the response carried, and one told the asker the link was "in the provenance metadata" — consumers repeat `text.message`, so it has to say the right thing to repeat. The banner is unchanged. Preregistered as E17; built by WO-6, verified O52 — served wording: `The start_char continuation is for the tool caller, not the person asking. A person who wants the whole document should be given the PDF link: <pdf_link>`; when the upstream download map carries no PDF link the sentence says so instead of emitting an empty URL (implementation claim, unobserved upstream, O52d). Corrected 2026-09-19: WO-6's `<pdf_link>` was the API-host link and returns 401 for the person it is addressed to (O53a); the URL is `public_pdf_link` from WO-7 on — built at c373a2e, verified O54: served wording `The start_char continuation is for the tool caller, not the person asking. A person who wants the whole document should be given the PDF link: <public_pdf_link>`, the continuation window included; the `details_link` fallback wording is unreachable by construction (implementation claim, consistent with every observed shape) and the no-link wording remains unobserved upstream (O54f).

**Secret hygiene.** The API key is sent only via the `X-Api-Key` header (R7, O22) and must never appear in any URL the server builds, logs, echoes, or surfaces. The outcome contracts above require exposing upstream URLs, bodies, and queries verbatim — that exposure is safe if and only if this rule holds, so a key found in any surfaced string is a contract violation twice over, and redaction is a backstop, not the mechanism. **The key goes to one origin (R18a, from S15 finding 2).** "Links are data, never constructed" obliges the server to fetch URLs that arrive inside upstream responses, and until 2026-09-20 nothing said to whom the header could be sent — so a malformed or compromised response could have walked the key to any host. The rule: `X-Api-Key` is attached only to a request whose URL has scheme `https`, host exactly `api.govinfo.gov`, the default port, and no userinfo — exact match, so `api.govinfo.gov.example.com`, `x.api.govinfo.gov`, `https://api.govinfo.gov@example.com/` and `:8443` all fail it. A link that fails it is not fetched at all — not with the key, and not without it either, since an off-origin link in a GovInfo response is a malformed response and fetching it keyless would still be the server making requests wherever upstream points. It surfaces as `upstream_error` with `http_status: null` and a `detail` that gives the refused URL verbatim, the field it came from, and the statement that nothing was requested — the no-response shape the server already serves (O57c); inside `possibly_superseded` it is `not_checked` with `reason: malformed_response`. Keyed requests never follow redirects: a 3xx is an `upstream_error` carrying the status and the `Location` verbatim. Both halves are free today — every upstream link in every run artifact is on that origin, 3,033 of 3,033 (O56), and no link kind redirects, 15 of 15 (O58) — and the rule is unexercisable against real upstream for the same reason, so its verification is unit-level and says so. The links the server hands to people (`public_pdf_link`, `details_link`, on `www.govinfo.gov`) are never fetched and are outside the rule. The spec defines no setting that moves the API base, and the served server has none: per the maintainer (S16) the only handle is an optional constructor argument on the client, defaulting to the real base, that nothing exposes — no environment variable, no flag — so in any running server the allowed origin is the constant above. For code that constructs the client directly (the tests), the allowed origin is the base it was constructed with, and plain `http` is tolerable only for a loopback address. Exposing that argument as a runtime setting would let configuration choose where the key goes; it is a contract change and needs a ruling, not a convenience to add in passing.

**Trace emission (R8).** When the `USCODE_MCP_TRACE_DIR` environment variable names a directory, every MCP request the server handles is appended as one JSONL line — a single JSON object containing at minimum the verbatim request (tool name and arguments as received) and the verbatim response (as returned, including error outcomes); a timestamp and extra fields are permitted, truncation of either payload is not. When the variable is unset, tracing is off and nothing is written — unset is the only off switch, there is no half-enabled state. A variable that is set but empty or whitespace is a configuration error and fails the server at startup like any other unusable directory, not a synonym for off: the instrument's off state must be unreachable by accident, because a harness that reads an empty trace as "nothing happened" has been lied to by a typo — a scan that errors must not look like one that found nothing, and that convention binds instruments hardest. File layout: the directory may contain one or more `*.jsonl` files (per-run naming is fine); the contract a harness may rely on is that every handled request appears exactly once across the directory's `*.jsonl` files, in chronological order within each file — so a harness globs, never assumes a single file. File mode (R18b, from S15 finding 4): every file the server creates in the trace directory is created readable and writable by its owner only — mode `0600`, set at creation and independent of the process umask — because trace lines hold callers' queries verbatim. Not required, deliberately: changing the directory's own mode, tightening files the server did not create, or symlink and name-collision defenses — the trace is a harness instrument switched on by an environment variable, not a multi-user facility, and machinery for a deployment nobody has is the dead-defensive pattern. Interaction with secret hygiene: under R7 the key lives only in the `X-Api-Key` upstream header, which is not part of any MCP request or response, so trace lines are key-free by construction — and if upstream detail (URLs, bodies) is ever added to trace lines, it inherits the same rule. The trace is a measurement instrument, so its failure modes follow instrument rules, not availability rules: an unusable trace directory fails the server at startup, and a per-request trace-write failure fails that request loudly rather than producing a silently incomplete trace — a trace missing lines poisons every conclusion a harness draws from it, which is worse than a refused request in a mode only test harnesses enable.

**Locating content in large payloads (R12).** Both text tools accept an optional `find` (case-insensitive literal substring): the response reports the true occurrence count, a capped list of offsets in the same coordinate system as `start_char`/`total_chars`, and short context snippets; zero matches is an explicit outcome. `get_us_code_section` successes additionally carry a `structure` block — the payload's ordered fields (`statute`, `sourcecredit`, typed notes with their headings) with `start_char` and exclusive `end_char` offsets taken from each field's own end marker — fields nest, so a container like `notes` spans its typed children — derived only from the upstream field markers (O36), degrading to a disclosed omission when markers are absent or unbalanced. Structure rides only on `start_char: 0` responses; nonzero-offset windows carry the omitted form with a pointer back (R13a — the block is invariant and was measured at 15× a small window). `structure.note` states that headings describe a field's opening, not its contents (R13b — a 38K "Findings" field held the entire RECA, O38). When the banner is present, the response's `text.message` states in-band that the banner is outside the offset coordinate system (R13c). One call locates; one call reads.

**Staleness indicator — `possibly_superseded` (R14, measured by O43, built and verified as WO-1/WO-2/WO-3, O44/O45/O46).** Every `get_us_code_section` success carries a `possibly_superseded` object — reading calls (nonzero `start_char`) included. It is an indicator in both directions and never a certification: when it fires, it says a later public law is indexed against this section — not that the text returned is out of date (the listed law may amend a different part of the section, may only cite it, or may not yet be effective; the server does not retrieve or parse enacting laws to find out, R14a); when it is silent, it says nothing about currency, because the index it queries misses one in seven listed (law, section) pairs (O43b) and one in four in an earlier sample (O21). Three states, never two, on a `status` discriminator: `laws_indexed` — carries the true upstream `count`, a capped `laws[]` of `{package_id, title, date_issued}` with `laws_shown`/`laws_cap`/`capped` and any capping stated in the message (the disambiguation-totals rule), and the fixed caveat, pinned verbatim (R14a addendum, O44f/O44g): "INDICATOR ONLY — NOT A FINDING THAT THE TEXT CHANGED. A listed law MENTIONS this section; that is all the index records. It may amend the section, amend something else and merely cite this one, waive it for a named party, or not yet be in effect. The verification set's own example: Public Law 119-74 is listed against 42 U.S.C. 2210 because one appropriations rider cites it in a parenthetical, and it amends nothing in the section. This server does not read enacting laws. YOU MUST READ THE LISTED LAW TO FIND OUT — get_public_law with its package_id, then search its text for this section. The list may also be incomplete: the index misses about one in seven listed (law, section) pairs." The wording is contractual; the tool description carries the same warning in shorter form; `none_indexed` — carries the fixed caveat that this is NOT a currency check and that absence of a match is not evidence the text is current; `not_checked` — with a `reason` (`upstream_error`, `rate_limited`, `transport_error`, `timeout`, `malformed_response`, `internal_error`, `no_bound`, `no_measured_citation_form`), the upstream HTTP status and body verbatim where a response existed, and 429 named as rate-limit with its headers — never collapsed into `none_indexed` (the three-outcomes rule binds here as everywhere). Every state echoes `checked_citation`, the exact upstream `query`, the `since` date, and `since_basis` (which `currentthrough` it came from). The query is `collection:PLAW lawtype:public publishdate:range({currentthrough + 1 day},) uscodecitation:"{title} U.S.C. {section}"` — `publishdate` because `approveddate` ranges return HTTP 500 upstream (O43f), bounded by the response's own `currentthrough` so it is correct for `year`-selected editions as well; `lawtype:public` because a live section was measured firing on a 119th-Congress private law whose package `get_public_law` refuses under R6, and the term composes cleanly and drops exactly that package (O44e; built as WO-2, verified O45). When `stripped_note` is true the check ran against the parent section, and the object says so in-band (`note_statement`): note-codified material is the case the index is measured weakest on (O17/O18, O43b) and a law affecting only the note may be indexed against neither citation. Appendix sections: numbered appendix sections have a measured field form, `"{title} U.S.C. App. {section}"` (O44d) — the detector runs on it, with `checked_citation` carrying the App. form (WO-2, O45); appendix rules (`28 U.S.C. App. Rule N`) and bare appendix citations have no measured form and return `not_checked` with `reason: no_measured_citation_form`, `query: null`, `checked_citation: null`, which is the honest outcome, not a defect. No current-edition appendix section was found that fires under the bound (report enumeration, O45c) — the fired appendix example on record is the 2014 edition of `50 U.S.C. App. 2012`. Cost and ordering (O44c, correcting the earlier assumption that the detector was independent of the text fetch): the bound needs `currentthrough`, which only the fetched HTML carries, so the first lookup of an edition in a server process issues the detector after the fetch (`issued: after_fetch`, ~+280 ms wall-clock measured keep-alive, n=10) and later lookups of that edition issue it before the citation search on the remembered `currentthrough`, verified against the payload and re-issued on mismatch (`issued: before_search`, ~+6 ms). Only `currentthrough` per edition is remembered; detector results are never reused across lookups. A detector failure never fails the lookup; the wait after the text is ready is bounded (2.0 s, then `timeout`). Firing policy: on every success, unconditionally (R14b, closed by the maintainer's Q13 answer 2026-09-15); no opt-in argument.

**Server instructions (the MCP `instructions` string hosts inject; maintainer-flagged as out of date 2026-09-15, rewritten as WO-3 and verified equal to the reference text, O46a).** Required content, in this order: (1) what the server is — codified US Code by annual edition plus public laws, with `currentthrough` on every text response as the staleness disclosure; (2) that `possibly_superseded` runs automatically on every `get_us_code_section` success — the consumer does not need to run the composition recipe to get the check, because the server has already run exactly that query and echoes it; (3) what each state means for the consumer's next move: `laws_indexed` — a listed law *mentions* the section, read it with `get_public_law` to find out whether the text changed; `none_indexed` — repeating the same query by hand is redundant, and silence is not evidence of currency because of the measured recall gap (O21, O43b), so the only further moves are widening the query (drop the date bound, try `search_public_laws` full text) or reading the source credits in the section itself; `not_checked` — the echoed `query` is the manual retry; (4) the composition recipe, kept, but framed as the widening step rather than the first step. Reference text the implementation may use verbatim follows; it is contractual in content, not in wording.

> Search and retrieval over the United States Code and Public Laws as published by GPO on GovInfo. The US Code tools serve the codified law by annual edition (annual editions lag enactment by 18+ months); every text response carries a `currentthrough` date as the staleness disclosure. For law enacted after that date — or law that never enters the Code at all — use the public-law tools.
>
> You do not need to check for later laws yourself: every `get_us_code_section` success already carries `possibly_superseded`, a three-state indicator (`laws_indexed` / `none_indexed` / `not_checked`) computed on every call by querying GovInfo for public laws published after that edition's `currentthrough` and indexed against the section. It is an indicator, never a certification. `laws_indexed` means a listed law MENTIONS the section — it may amend it, amend something else and merely cite it, or waive it for one named person; read the law with `get_public_law` to find out. `none_indexed` means the server's query found nothing — re-running the same query by hand will find nothing more, and it is NOT evidence the text is current: the index misses about one in seven listed (law, section) pairs. `not_checked` means the check failed and says nothing either way; the echoed `query` is your manual retry. Read the object's `caveat`.
>
> To widen beyond what the indicator ran: `search_public_laws` with the echoed `query` minus its `publishdate` bound, or a full-text search over the public-law collection; and read the section's own source credits for the amendment history GovInfo prints.

**Wire shape, noted and accepted (O40).** Responses carry the envelope twice — `structuredContent` (typed; what the Layer-1 checks point at) and its JSON serialization in `content[0].text` (what hosts inject into model context, per the MCP dual-emission convention). Model-context cost is 1×; the duplication is wire/trace-side and accepted. Do not "fix" one copy away: the text copy is host visibility, the structured copy is the instrument.

**Collection scoping (R17, measured by O55; build order WO-8).** Each search tool runs in exactly one collection — `search_us_code` in USCODE, `search_public_laws` in PLAW — and the caller's `query` cannot move it. Corrected 2026-09-20: the contract had said the server prepends its collection "unless the query already contains a `collection:` term", which licensed any collection at all; the served server did exactly that, returning PLAW and BILLS hits from `search_us_code` and a US Code hit under the public-law `recall_caveat` from `search_public_laws` (O55a). The rule: the server finds every collection clause in `query` — the letters `collection`, in any letter case, followed by optional whitespace and a colon, **anywhere in the string**: nothing exempts an occurrence, not double quotes, not parentheses, not whatever characters precede it (`subcollection:` counts). Corrected 2026-09-20 (O57e): the rule as first issued exempted a clause "outside a double-quoted phrase", and WO-8, built faithfully to it, was measured letting `"fair use collection:PLAW` through — one unbalanced quote, 11 USCODE + 7 PLAW hits — because upstream does not treat an unterminated or escaped quote as opening a phrase; the server must not run a quote parser that can disagree with upstream's, so it runs none. The clause's value is everything after the colon up to the next whitespace, closing parenthesis, or end of the query — or, when the value opens with a double quote, through the next double quote, which must itself be followed by whitespace, a closing parenthesis, or the end. A clause conforms only if that whole value is the tool's own collection, bare or double-quoted, in any letter case, written with no whitespace after the colon — `collection:USCODE*`, `collection:USCODE,PLAW` and the like do not conform (O57f: the first build read the value only up to the first non-word character and sent them upstream, where each returned HTTP 500) (`collection:USCODE`, `collection:uscode`, `COLLECTION:"USCODE"` — the spellings upstream was measured to honor, O55b). If every clause conforms, the query goes upstream as the caller wrote it, with the tool's canonical clause prepended only when the query carries none — so the `possibly_superseded` recipe, whose echoed `query` begins `collection:PLAW`, pastes into `search_public_laws` unchanged. If any clause does not conform — another collection, a parenthesized value list, the space-after-colon form, a negated clause, an empty value — the call is refused before any upstream request with `outcome: out_of_scope_collection` (the shape of `out_of_scope_private_law`): the offending clause verbatim, the tool's collection, the tool that serves the named collection when there is one (`collection:PLAW` on `search_us_code` points at `search_public_laws`, and the reverse), and a statement that no search was run — a refusal must not read as zero results. Why refusal and not repair: upstream unions repeated collection terms wherever they sit, `collection:USCODE collection:PLAW` and `collection:USCODE (collection:PLAW …)` both returning the two collections' hits added together (O55c), so prepending the right clause next to a wrong one scopes nothing, and silently deleting the caller's clause would run a query they did not write. Why the space form is refused rather than ignored: upstream does not read `collection: USCODE` as a restriction (O55d), so a caller who writes it believes in a scope that does not exist; the rule is deliberately conservative — a negated foreign clause was measured harmless (O55c) and is refused anyway, because the validator's job is to be obviously right, not to model upstream's grammar. The cost, accepted: a phrase search for the literal text `collection:` — `"the collection: of duties"` — is refused, and the refusal message says to write the phrase without the colon; the one such phrase measured returned zero hits anyway (O57d). Conforming clauses need no operator analysis: upstream lifts collection clauses out of the boolean structure and filters on their union, so `"fair use" AND NOT collection:USCODE` and `"fair use" OR collection:USCODE` both return the in-collection set (O57g) — finding every clause upstream would find is the whole job. Not required: parenthesizing the caller's query. A top-level `OR` was measured not to escape a prepended clause — bare and parenthesized forms returned identical counts, 100 of 100 page hits in-collection (O55e, the preregistered escape falsified). The citation-resolution and detector queries the server builds itself are outside this rule; it binds the `query` argument of the two search tools. `get_us_code_section` and `get_public_law` take no query and are unaffected.

**Links are data, never constructed.** Download URLs come from search results and summaries verbatim (settled, `00-INDEX.md`).

**Text derivation.** The `/htm` payload is HTML (O5). The server strips it to readable plain text (preserving the header block that identifies edition and hierarchy) and returns that; it does not return raw HTML by default. No statutory content may be dropped — and after O15 "content" explicitly includes everything after the statutory text: source credits and statutory notes are the payload's majority for note-heavy sections and are the entire point for note citations (R4).

## `get_us_code_section`

Resolve a citation and return the section's text, notes included.

Arguments: `citation` (string — accepts "17 U.S.C. 107", "17 USC 107", "17 U.S.C. § 107(b)", "42 U.S.C. 2210 note", or equivalently `title` + `section` as separate fields), optional `year` (edition year), optional `max_chars`/`start_char`. Optional `granule_id` (R16): a USCODE granule id exactly as a disambiguation list or `search_us_code` result carried it, with optional `package_id` alongside; when present it selects the granule directly and the citation search is skipped — `citation` may still be supplied with it, and is then used for the staleness detector (below); `year` is ignored with a warning in the response, since the id names its edition.

Behavior: normalize per `30-search.md` — mandatory strips: parenthetical subsection (O11) and trailing "note" (O16); when either strip fires, the response says so and names the containing section it resolved instead. Search `collection:USCODE citation:"…"` with `historical` set iff `year` given; on multiple hits after year filtering, return the disambiguation list (ids + titles) rather than guessing — and the list must carry the true total from the response's `count` alongside however many candidates fit the page, with any capping stated, so 100 shown of 251 (the measured bare-appendix case, O24) never reads as 100 of 100; fetch the winning granule's `txtLink` and, concurrently, run the `possibly_superseded` detector query (cross-cutting contract above); return text + provenance + the three-state staleness indicator. A citation that resolves to zero granules reports the normalized citation and the raw query so the caller can retry with `search_us_code`. The disambiguation message names the actual re-request path: `granule_id` from the list (R16), or `year` when the candidates differ by edition — never an input the tool does not accept (the pre-R16 wording "by ids" promised one, O45c).

By-id behavior (R16, WO-3): with `granule_id`, the server does not construct any URL from the id. It fetches the granule summary — `GET /packages/{package_id}/granules/{granule_id}/summary`, the endpoint measured in O9 — and takes `txtLink` from it verbatim (the links-verbatim rule, O4). `package_id` comes from the argument when given; otherwise from the id's leading `USCODE-{year}-title{n}` segments, which is the one piece of id structure this spec relies on (measured shape, O9/O14) and is disclosed as `package_id_derived: true` in the response. Provenance, `currentthrough`, windowing, `find`, `structure`, and the banner are identical to the citation path — the payload is the same `/htm` document. Outcomes (measured O46c, ratifying the implementation's correction of this spec's earlier "404"): the summary endpoint answers **400 `invalid granuleId`** for any nonexistent granule under a real package (wrong section, wrong chapter, wrong edition, wrong title, garbage — 6 of 6 shapes) and **404** only for a nonexistent package (2 of 2); both are `not_found`, distinguished by `not_found_kind: granule | package`, with the upstream status and body echoed and the id named; any other 400, and every 5xx, stays `upstream_error`, and 429 stays rate-limited — a failure never reads as "not found". A non-USCODE id is rejected as `invalid_argument` before any call. Staleness detector on the id path: it needs a `{title} U.S.C. {section}` form, and the granule summary's `usCodeCitation` was measured null (O9), so the detector runs on the supplied `citation` after the usual strips when one is given, and otherwise reports `not_checked` with `reason: no_citation_for_detector` and a message saying to pass `citation` alongside `granule_id` to get the check. **The supplied citation is the caller's word, and the response says so (O61d, from S17 finding 2).** Served at 633e61c, the title 17 § 107 granule with `citation: "42 U.S.C. 2210"` came back `success` with title 17's text, `normalized_citation: 42 U.S.C. 2210`, a `laws_indexed` staleness result for the title 42 section, and no warning. Two rules. (1) Title check, before any upstream request: the citation's title must equal the `title{n}` of the package id — supplied or derived, the same leading segments this contract already relies on; a mismatch is `invalid_argument` naming both titles and stating that nothing was fetched. (2) The section is not checkable from the id — granule ids nest five levels and this spec relies on none of it (O14) — and the summary's `usCodeCitation` is null (O9), so on every id-path success with a `citation` the response discloses the basis instead of implying a resolution: `normalization.citation_basis: caller_supplied` (the citation path carries `resolved`), and `possibly_superseded` carries a `citation_statement` in-band — the check ran on the citation the caller supplied, which the server did not verify names this granule; if it does not, this result is about a different section. Not required, deliberately: confirming membership by running the citation search and looking for the granule id among its hits. It is the principled check (identity, not strings), it costs the search the id path exists to skip, and the round trip this path was built for — list → pick → `granule_id` + the original `citation` — cannot mismatch; it becomes the rule if a consumer is measured pairing an id with the wrong section in the same title. The disambiguation list already carries `package_id` and `granule_id` per candidate (measured in the WO-2 artifacts, O45), so the round trip is list → pick → `granule_id` + the original `citation`.

Appendix citations ("28 U.S.C. App. …"): resolved directly — E10 found the form (O24, falsifying the earlier no-direct-form assumption): normalize to `citation:"{title} U.S.C. App."` plus any rule/section qualifier and search as usual. Multi-hit responses (measured: "28 U.S.C. App. Rule 9" → two granules, O24) use the standard disambiguation-list behavior. ## `search_us_code`

Full-text and fielded search over the USCODE collection — the discovery path for topics, appendix material (O19), and anything citation resolution redirects here.

Arguments: `query` (govinfo query syntax; the server prepends `collection:USCODE` when the query carries no collection clause; a clause naming USCODE is accepted, any other collection clause is refused with `out_of_scope_collection` before any upstream request — "Collection scoping" above, R17), optional `page_size` (default 20, max 100), `offset_mark` (default `*`), `historical` (default false).

Returns: `count`, next `offset_mark`, and per hit: `title`, `packageId`, `granuleId`, `dateIssued`, download links. It returns pointers, not text — the caller follows up with `get_us_code_section` (or the ids directly).
