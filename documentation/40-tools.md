# MCP tool surface

Four tools. Small on purpose: each maps to one recipe in `30-search.md`, and everything else (summaries, alternate formats) rides along as links in responses rather than as more tools.

## Cross-cutting contracts

These bind every tool:

**Three distinct outcomes, never collapsed.** (1) Success, possibly with zero results — a zero-hit search says so explicitly and echoes the exact query sent upstream. (2) Upstream failure — HTTP status and body surfaced; a failed call must never present as "not found". (3) Rate-limited — HTTP 429 surfaced as its own outcome with `x-ratelimit-*`/`Retry-After` information passed through (limit measured at 36,000/hr, O13 — headroom is real but the contract doesn't depend on it). A 2xx whose body is not the shape the server reads — not JSON, `results` not a list of objects, a summary that is not an object, a required field of the wrong type — is outcome (2): `upstream_error` with the HTTP status, the body verbatim, and a `detail` naming what was expected and what arrived; inside `possibly_superseded` it is `not_checked` / `malformed_response`, as already specified. It must never leave the tool as an unhandled exception, because a host shows that as a generic tool failure with no status, no body and no query — a failed call that says nothing about why is one step from reading as "not found". Added 2026-09-20 from S17 finding 3, a claim about code this session cannot observe; no wrongly-typed 2xx body appears in any run artifact (O61f), so this is cheap insurance at the one place bodies are parsed, verified at unit level only, and not a licence for per-field defensive machinery.

**Failure bodies are bounded only out loud (S32 finding 2).** The upstream body relayed with outcome (2) or (3), or inside `possibly_superseded` as `not_checked`, is verbatim when it is relayed whole. The server may bound it — an error page can be long, and a failure is no reason to flood the caller's context — but a cut body is never presented as the body: the envelope says it was cut and gives the full body's length in characters beside the part relayed, which is the body's opening characters unaltered. Where the bound sits, and whether 429 and other failures share it, is the implementation's call, stated in its report and ratified here with the field names. Ratified from WO-26 B (O116a): the bounds are the ones served before the order — 5,000 characters for `upstream_error`, 2,000 for `rate_limited`, 5,000 inside `possibly_superseded.not_checked` (500, 429 and malformed bodies alike, so a 429 body under 5,000 is whole there and cut only as a top-level `rate_limited`), 2,000 for the by-id `not_found` summary body; within the bound `body` alone, verbatim; over it `body` is the opening characters unaltered with `body_cut: true`, `body_total_chars`, `body_shown_chars` (the bound) and `body_note`: "The upstream body was cut: 'body' is its first {bound} characters of {total}; nothing after that point is relayed." with thousands separators. Added 2026-09-29 from S32 finding 2, a claim (a 6,000-character 500 body relayed as 5,000 characters and a 3,000-character 429 body as 2,000, neither disclosed); it carries "No silent truncation", written for text windows, to failure bodies, which that rule did not name. GovInfo cannot be made to fail on demand, so this is verified at unit level.

**Provenance on every text payload.** Any response containing statutory text states: `packageId`, `granuleId` (when granule-level), edition year, the `currentthrough` date parsed from the granule HTML comment (O5, O15), `lastModified`, and three links: `pdf_link` (the upstream `download.pdfLink`, on `api.govinfo.gov`, requires the key — for the tool caller), `public_pdf_link` (`https://www.govinfo.gov/content/pkg/{package_id}/pdf/{package_id}.pdf` for a package, `…/pdf/{granule_id}.pdf` for a granule, built from the response's own identifiers and nothing else; opens without a key, O53b/c — for a person), and `details_link` (the upstream `detailsLink` verbatim, the document page, no key, O53d — the fallback that assumes no URL pattern). `details_link` is null on the citation path of `get_us_code_section`: that path resolves through a search hit and fetches no summary, and search hits carry no `detailsLink` on either collection (O54d, measured by both sessions); the null is accepted and disclosed rather than bought with a granule-summary fetch per citation lookup, because `package_id` is present on every path where `details_link` could be, so `public_pdf_link` is always built and the fallback never fires — revisit if a consumer is measured wanting the details page rather than the PDF. Corrected 2026-09-19 (O53): the contract had said "the canonical PDF link" without naming a host, the implementation took `download.pdfLink`, and WO-6 wrote that key-requiring URL into the sentence addressed to the person asking — a link they cannot open. WO-7, built at c373a2e and verified O54: every served `public_pdf_link` opened without a key, 7 of 7 across both tools, two historical editions, and an appendix granule. If `currentthrough` cannot be parsed, say so — do not omit silently. Given the backend ruling (R1), `currentthrough` is the staleness disclosure and is non-optional.

**No silent truncation.** Text responses take an optional `max_chars` (default **20000** — lowered from 100,000 on 2026-09-16 per E15/O47: a 100,082-char window was measured NOT delivered inline to the model by claude-code 2.1.236, which counted it and substituted a ~3 KB stand-in, while a 20,081-char window in the same cell was delivered inline; the default sits just under the largest window measured to arrive, and a consumer that wants more asks for it explicitly; the threshold is a host property and is re-measured when the driver changes — WO-4) and `start_char` (default 0). When the payload exceeds the window, the response states total length, the window returned, and the `start_char` to continue from. Full text is never elided without these markers. **Window arguments are checked where they can be (O61e, from S17 finding 4).** What is decidable from the arguments alone — `max_chars` ≤ 0, `start_char` < 0, a non-integer — is `invalid_argument` before any upstream request; served at 633e61c these refusals took 542–1,166 ms against 6 ms for a locally-refused control, a full lookup spent to reject an argument, and against a 36,000/hr budget (O13) that is quota a malformed loop can burn. What needs the payload is decided after it: **The `max_chars` ≤ 0 refusal names the locating spelling (2026-09-22, from two consumers measured asking for it: O75, and `70-run-findings.md` run 20260922T120550Z).** Its `detail` says that `max_chars` must be at least 1, and that a call meant only to locate — `structure`, or `find` — should pass `max_chars: 1`, which returns the map and the occurrences with one character of text. `max_chars: 0` is not given a meaning of its own: a zero-width window would need its own banner and truncation semantics, and the one-character call already does the job (O64c: 3,791 characters of envelope). Built as WO-13 part D, verified O79 — served `detail` on both tools: `max_chars must be at least 1, got 0. For a locating call that returns \`structure\` or \`find\`, pass \`max_chars: 1\`.`, with no upstream request. a `start_char` greater than zero and at or past `total_chars` is `invalid_argument` carrying `total_chars` and saying that no text exists at that offset and that the document was retrieved and is not empty — never `success` with an empty window and `truncated: false`, which is what was served and which reads as an empty document. `start_char: 0` on an empty payload remains a `success`. A consumer following `next_start_char` cannot reach this case, since the last window's is null; one doing its own arithmetic can. **The markers must also live in a stream the model reads (E12; the carrier changed with WO-13, below).** From 2026-09-01 until WO-13 landed, `text.content` began, when `truncated` was true, with a single bracketed banner line stating the window bounds, the true total, and the continuation `start_char` (e.g. `[WINDOW chars 0–99,999 of 3,590,552 — truncated; continue with start_char=100000]`); the line now lives in `text.banner` alone. Ruled 2026-09-01 from finding F1 (`70-run-findings.md`): a floor consumer, given complete and correct structured truncation fields, still presented the window as the whole law — the disclosure has to sit in the stream the model actually reads, not only beside it. Preregistered as E12. Load-bearing in both collections: a section granule reached 142KB (O15) and a public law is a single multi-thousand-page package (O8). **The message must also address the audience.** When `truncated` is true, `text.message` — the in-band prose channel (R13c) — states, after the continuation, that the `start_char` continuation is for the tool caller, and that a person asking for the whole document should be given the PDF link, with the response's `public_pdf_link` written into the sentence — never `pdf_link`, which 401s without the key (O53a), and never a pointer to the field (e.g. `Continue with start_char=20000. That continuation is for you, the tool caller; if the person asking wants the whole document, give them the PDF: https://www.govinfo.gov/content/pkg/PLAW-118publ31/pdf/PLAW-118publ31.pdf`). When `public_pdf_link` cannot be built, the sentence gives `details_link`; when neither exists, it says no link is available. Ruled 2026-09-18 from F7 (`70-run-findings.md`; O51c): under the harness's loop driver, 21 of 21 C1 answers relayed the continuation to the asker verbatim, 0 of 10 pinned answers offered the PDF link the response carried, and one told the asker the link was "in the provenance metadata" — consumers repeat `text.message`, so it has to say the right thing to repeat. The banner is unchanged. Preregistered as E17; built by WO-6, verified O52 — served wording: `The start_char continuation is for the tool caller, not the person asking. A person who wants the whole document should be given the PDF link: <pdf_link>`; when the upstream download map carries no PDF link the sentence says so instead of emitting an empty URL (implementation claim, unobserved upstream, O52d). Corrected 2026-09-19: WO-6's `<pdf_link>` was the API-host link and returns 401 for the person it is addressed to (O53a); the URL is `public_pdf_link` from WO-7 on — built at c373a2e, verified O54: served wording `The start_char continuation is for the tool caller, not the person asking. A person who wants the whole document should be given the PDF link: <public_pdf_link>`, the continuation window included; the `details_link` fallback wording is unreachable by construction (implementation claim, consistent with every observed shape) and the no-link wording remains unobserved upstream (O54f). **Two carriers: `text.banner` and `text.message`; `text.content` is the payload and nothing else (E22, O76; ruled by the decision rule pinned in E22 under R21, 2026-09-21).** When `truncated` is true, `text.banner` carries the banner line verbatim (the pinned wording above, e.g. `[WINDOW chars 0–19,999 of 3,590,552 — truncated; continue with start_char=20000]`), `text.message` carries the continuation and the audience sentence, and `text.content` begins with the first character of the window — no banner line, so no coordinate disclaimer is needed and the R13c sentence is retired. History: the banner line inside `text.content` was E12's mitigation for F1 and shipped alongside a `text.banner` field this spec never specified; the two were never served apart (O65), so nothing said which one worked. E22 separated them on `gpt-oss-120b` at the floor: with the field alone, no answer quoted the banner (M3 0 of 18) and the continuation offset reached the asker in 2 of 18 against 9 of 19 with both — the model pastes `text.content` and whatever leads it — while the F1 failure appeared in no arm and the C1 pass rate was equal. The content line was the source of the parroting the maintainer reported (F13). The `USCODE_MCP_BANNER_CARRIERS` switch is removed with this change. Built as WO-13 at `0436218`, verified O79 (2026-09-23): `text.content` begins at the window's first character on every truncated call, `text.banner` is present exactly when `truncated` is true, `returned_chars` equals the content length, the R13c sentence is gone and the switch is gone; the served shape is byte-equal to the `field` mode measured at O66. The manifest's banner check reads `text.banner` from version 7. Whatever is served, the carriers state the window the same way — the banner's inclusive bounds, which are pinned character-exact (O37): served, `text.message` said "returned chars 0-6000" beside a banner saying "chars 0–5,999", and a consumer doing arithmetic from one of them is off by one against the other.

**A window ends where a paragraph does (R36; measured O121; build order WO-31; consumer effect E43).** `max_chars` is an upper bound on `text.content`, not its length. Served through WO-30, a window was exactly `max_chars` characters and ended wherever that fell — mid-word in the measured case ("in accordance with the applicable pro"), and a floor consumer finished the sentence from memory in 4 of 10 rows (O120d; F17, O107b). From WO-31, on both text tools and for every `start_char`, a window that would stop short of the payload's end is ended by the first of these that applies. **(1) As asked,** when the requested end already sits at a paragraph break — immediately before or after a blank line. Every `structure` field ends there (1,863 of 1,863 field ends, O121d), so a field read by its own coordinates, `max_chars` = `end_char` − `start_char`, is returned whole and unchanged. **(2) At the last paragraph break inside the window,** when the text up to and including that break is at least half of `max_chars`; the window ends just after the blank line, so the next window opens on a paragraph's first character. **(3) At the last whitespace inside the window,** when no break keeps half — a paragraph longer than the window, which exists (3,099 characters in `7 U.S.C. 2020`; 280 of 1,128 windows at `max_chars` 500, 4 of 216 at 2,000, none at 5,000 or 20,000; O121b, f) — so that no word is split. **(4) As asked,** when the window holds no whitespace at all (the `max_chars: 1` locating call). A paragraph break is two or more consecutive newlines in the payload as served; a single newline is not one — in a public law it is a line wrap inside a sentence (O121b). Sentence punctuation is never a boundary: in this corpus a period followed by a space is a citation more often than a sentence end ("42 U.S.C. 2210", "28 U.S.C. App.", "Pub. L."; O121e; R36b). No window is lengthened and no character is skipped or served twice: `returned_chars` is the length actually returned, `next_start_char` is `start_char` + `returned_chars`, and the banner and message state the bounds actually returned, in the pinned forms. **What the response says.** A truncated `text` carries `requested_max_chars` (the `max_chars` in force) and `ends_at`: `"paragraph"` for (1) and (2), `"word"` for (3), `"character"` for (4). Every existing marker stays (R36c): `truncated`, `total_chars`, `returned_chars`, `next_start_char`, `text.banner`, and in `text.message` the size sentence, the continuation, and the audience sentences, in that order and worded as before. One sentence is inserted after the size sentence and before "Continue with start_char=…". For `"paragraph"` when the window is shorter than asked: "The window ends at a paragraph break, {requested_max_chars − returned_chars} chars before the {requested_max_chars} asked for, so that no sentence is cut; max_chars is an upper bound." For `"paragraph"` at full length: nothing is inserted. For `"word"` and `"character"`: "The window ends inside a paragraph: its last sentence is incomplete. Do not complete it or describe what follows; the rest is in the next window." A window that reaches the payload's end is not truncated and carries none of this. **Not done, on purpose.** A window may end just after a heading whose body is in the next window (the appellate Rule 9 at `max_chars` 3,000 ends after "Notes of Advisory Committee on Rules—1967"; O121f): telling a heading from a short paragraph is a parse of the text, and the message already says the window is truncated. `find` offsets and snippets, `structure`, the default of 20,000 and the tool descriptions are unchanged — "`max_chars` = `end_char` − `start_char`" in the description stays true under (1).

**Secret hygiene.** The API key is sent only via the `X-Api-Key` header (R7, O22) and must never appear in any URL the server builds, logs, echoes, or surfaces. The outcome contracts above require exposing upstream URLs, bodies, and queries verbatim — that exposure is safe if and only if this rule holds, so a key found in any surfaced string is a contract violation twice over, and redaction is a backstop, not the mechanism. **The key goes to one origin (R18a, from S15 finding 2).** "Links are data, never constructed" obliges the server to fetch URLs that arrive inside upstream responses, and until 2026-09-20 nothing said to whom the header could be sent — so a malformed or compromised response could have walked the key to any host. The rule: `X-Api-Key` is attached only to a request whose URL has scheme `https`, host exactly `api.govinfo.gov`, the default port, and no userinfo — exact match, so `api.govinfo.gov.example.com`, `x.api.govinfo.gov`, `https://api.govinfo.gov@example.com/` and `:8443` all fail it. A link that fails it is not fetched at all — not with the key, and not without it either, since an off-origin link in a GovInfo response is a malformed response and fetching it keyless would still be the server making requests wherever upstream points. It surfaces as `upstream_error` with `http_status: null` and a `detail` that gives the refused URL verbatim, the field it came from, and the statement that nothing was requested — the no-response shape the server already serves (O57c); inside `possibly_superseded` it is `not_checked` with `reason: malformed_response`. Keyed requests never follow redirects: a 3xx is an `upstream_error` carrying the status and the `Location` verbatim. Both halves are free today — every upstream link in every run artifact is on that origin, 3,033 of 3,033 (O56), and no link kind redirects, 15 of 15 (O58) — and the rule is unexercisable against real upstream for the same reason, so its verification is unit-level and says so. The links the server hands to people (`public_pdf_link`, `details_link`, on `www.govinfo.gov`) are never fetched and are outside the rule. The spec defines no setting that moves the API base, and the served server has none: per the maintainer (S16) the only handle is an optional constructor argument on the client, defaulting to the real base, that nothing exposes — no environment variable, no flag — so in any running server the allowed origin is the constant above. For code that constructs the client directly (the tests), the allowed origin is the base it was constructed with, and plain `http` is tolerable only for a loopback address. Exposing that argument as a runtime setting would let configuration choose where the key goes; it is a contract change and needs a ruling, not a convenience to add in passing.

**Trace emission (R8).** When the `USCODE_MCP_TRACE_DIR` environment variable names a directory, every MCP request the server handles is appended as one JSONL line — a single JSON object containing at minimum the verbatim request (tool name and arguments as received) and the verbatim response (as returned, including error outcomes); a timestamp and extra fields are permitted, truncation of either payload is not. When the variable is unset, tracing is off and nothing is written — unset is the only off switch, there is no half-enabled state. A variable that is set but empty or whitespace is a configuration error and fails the server at startup like any other unusable directory, not a synonym for off: the instrument's off state must be unreachable by accident, because a harness that reads an empty trace as "nothing happened" has been lied to by a typo — a scan that errors must not look like one that found nothing, and that convention binds instruments hardest. File layout: the directory may contain one or more `*.jsonl` files (per-run naming is fine); the contract a harness may rely on is that every handled request appears exactly once across the directory's `*.jsonl` files, in chronological order within each file — so a harness globs, never assumes a single file. File mode (R18b, from S15 finding 4): every file the server creates in the trace directory is created readable and writable by its owner only — mode `0600`, set at creation and independent of the process umask — because trace lines hold callers' queries verbatim. Not required, deliberately: changing the directory's own mode, tightening files the server did not create, or symlink and name-collision defenses — the trace is a harness instrument switched on by an environment variable, not a multi-user facility, and machinery for a deployment nobody has is the dead-defensive pattern. Interaction with secret hygiene: under R7 the key lives only in the `X-Api-Key` upstream header, which is not part of any MCP request or response, so trace lines are key-free by construction — and if upstream detail (URLs, bodies) is ever added to trace lines, it inherits the same rule. The trace is a measurement instrument, so its failure modes follow instrument rules, not availability rules: an unusable trace directory fails the server at startup, and a per-request trace-write failure fails that request loudly rather than producing a silently incomplete trace — a trace missing lines poisons every conclusion a harness draws from it, which is worse than a refused request in a mode only test harnesses enable.

**Locating content in large payloads (R12).** Both text tools accept an optional `find` (case-insensitive literal substring): the response reports the true occurrence count, a capped list of offsets in the same coordinate system as `start_char`/`total_chars`, and short context snippets; zero matches is an explicit outcome. `get_us_code_section` successes additionally carry a `structure` block — the payload's ordered fields (`statute`, `sourcecredit`, typed notes with their headings) with `start_char` and exclusive `end_char` offsets taken from each field's own end marker — fields nest, so a container like `notes` spans its typed children — derived only from the upstream field markers (O36), degrading to a disclosed omission when markers are absent or unbalanced. Structure rides only on `start_char: 0` responses; nonzero-offset windows carry the omitted form with a pointer back (R13a — the block is invariant and was measured at 15× a small window). `structure.note` states that headings describe a field's opening, not its contents (R13b — a 38K "Findings" field held the entire RECA, O38). R13c — that `text.message` say in-band that the banner is outside the offset coordinate system — was retired by WO-13 (O79): no banner is inside `text.content` any more, so offsets and content share one coordinate system and there is nothing to disclaim. One call locates; one call reads. **The locating call can be small, and the description says so (O64c, from S18).** `structure` rides on any `start_char: 0` response whatever its `max_chars`; on `17 U.S.C. 107` a `max_chars: 1` call was 3,791 characters of envelope against 24,053 for the default window, and the median over 151 uniformly sampled sections was 3,518 (O64e). A consumer that had used the tool successfully still reported "no cheap way to look before reading" (S18), because the served description said `structure` comes back on the locating call and never that a locating call may ask for almost nothing. The `get_us_code_section` description must teach both halves in a sentence or two: the statutory text is the first field after a short header (median offset 380, O64e), so for "what does the statute say" a `max_chars` of 6,000 returns `statute` and `sourcecredit` whole in 111 of the 134 sampled sections that have a `statute` field (O64e), together with the map of everything behind them; and when a section's size is unknown, a small `max_chars` buys the map alone.

**Staleness indicator — `possibly_superseded` (R14, measured by O43, built and verified as WO-1/WO-2/WO-3, O44/O45/O46).** Every `get_us_code_section` success carries a `possibly_superseded` object — reading calls (nonzero `start_char`) included. It is an indicator in both directions and never a certification: when it fires, it says a later public law is indexed against this section — not that the text returned is out of date (the listed law may amend a different part of the section, may only cite it, or may not yet be effective; the server does not retrieve or parse enacting laws to find out, R14a); when it is silent, it says nothing about currency, because the index it queries misses one in seven listed (law, section) pairs (O43b) and one in four in an earlier sample (O21). Three states, never two, on a `status` discriminator: `laws_indexed` — carries the true upstream `count`, a capped `laws[]` of `{package_id, title, date_issued}` with `laws_shown`/`laws_cap`/`capped` and any capping stated in the message (the disambiguation-totals rule), and the fixed caveat, contractual verbatim (drafted by this session under R23, 2026-09-23; built as WO-14 at `e0165f5`, verified served character for character, O83): "INDICATOR ONLY — NOT A FINDING THAT THE TEXT CHANGED. A listed law MENTIONS this section; that is all the index records. It may amend the section, amend something else and merely cite this one, waive it for a named party, or not yet be in effect. The verification set's own example: Public Law 119-74 is listed against 42 U.S.C. 2210 because one appropriations rider cites it in a parenthetical, and it amends nothing in the section. This server does not read enacting laws. The list may also be incomplete: the index misses about one in seven listed (law, section) pairs. What follows is for the tool caller, not the person asking. To find out whether the text changed, read the listed law before answering: call get_public_law with its package_id, then find this section in its text. If the listed law is not read, tell the person asking, in plain words, that a later law mentions this section and has not been checked — and do not pass on tool names, package ids or field names, which the person cannot use." Before WO-14 the served wording was the R14a-addendum one (O44f/O44g), identical up to the last two sentences, which read "YOU MUST READ THE LISTED LAW TO FIND OUT — get_public_law with its package_id, then search its text for this section." before the incompleteness sentence; F9 measured a floor consumer taking that "you" as the person asking and relaying the recipe (O67b), and the redraft names the reader on the pattern WO-6 measured to work in `text.message` (E17, O76). The wording is contractual; the tool description carries the same warning in shorter form, already in the third person, and is unchanged by WO-14; `none_indexed` — carries the fixed caveat that this is NOT a currency check and that absence of a match is not evidence the text is current; `not_checked` — with a `reason` (`upstream_error`, `rate_limited`, `transport_error`, `timeout`, `malformed_response`, `internal_error`, `no_bound`, `no_measured_citation_form`), the upstream HTTP status and body verbatim where a response existed, and 429 named as rate-limit with its headers — never collapsed into `none_indexed` (the three-outcomes rule binds here as everywhere). Every state echoes `checked_citation`, the exact upstream `query`, the `since` date, and `since_basis` (which `currentthrough` it came from). The query is `collection:PLAW lawtype:public publishdate:range({currentthrough + 1 day},) uscodecitation:"{title} U.S.C. {section}"` — `publishdate` because `approveddate` ranges return HTTP 500 upstream (O43f), bounded by the response's own `currentthrough` so it is correct for `year`-selected editions as well; `lawtype:public` because a live section was measured firing on a 119th-Congress private law whose package `get_public_law` refuses under R6, and the term composes cleanly and drops exactly that package (O44e; built as WO-2, verified O45). When `stripped_note` is true the check ran against the parent section, and the object says so in-band (`note_statement`): note-codified material is the case the index is measured weakest on (O17/O18, O43b) and a law affecting only the note may be indexed against neither citation. Appendix sections: numbered appendix sections have a measured field form, `"{title} U.S.C. App. {section}"` (O44d) — the detector runs on it, with `checked_citation` carrying the App. form (WO-2, O45); appendix rules (`28 U.S.C. App. Rule N`) and bare appendix citations have no measured form and return `not_checked` with `reason: no_measured_citation_form`, `query: null`, `checked_citation: null`, which is the honest outcome, not a defect. No current-edition appendix section was found that fires under the bound (report enumeration, O45c) — the fired appendix example on record is the 2014 edition of `50 U.S.C. App. 2012`. Cost and ordering (O44c, correcting the earlier assumption that the detector was independent of the text fetch): the bound needs `currentthrough`, which only the fetched HTML carries, so the first lookup of an edition in a server process issues the detector after the fetch (`issued: after_fetch`, ~+280 ms wall-clock measured keep-alive, n=10) and later lookups of that edition issue it before the citation search on the remembered `currentthrough`, verified against the payload and re-issued on mismatch (`issued: before_search`, ~+6 ms). Only `currentthrough` per edition is remembered; detector results are never reused across lookups. A detector failure never fails the lookup; the wait after the text is ready is bounded (2.0 s, then `timeout`). That sentence binds against every shape, including a well-formed detector envelope whose `results` elements are not objects — `not_checked` with `reason: malformed_response` and the body echoed, never an exception out of the tool (S26 finding 1, reproduced offline; WO-15 A). `not_checked` reasons are true statements under the three-outcomes rule: `no_bound` with "the query was not sent" is served only when no query was sent — a bound error from a remembered `currentthrough` does not outlive the launch that follows on the payload's own date, a query that is sent is waited for or cancelled and never silently discarded — when a speculative query on a remembered bound was already sent and the payload then yields no usable bound, it is cancelled, `query` and `since` are null, and a `prediction_note` says the speculative query was issued and cancelled (O87f) — and a remembered `currentthrough` that does not parse as a date is not remembered (S26 finding 3; WO-15 C, verified O87). Firing policy: on every success, unconditionally (R14b, closed by the maintainer's Q13 answer 2026-09-15); no opt-in argument.

**Server instructions (the MCP `instructions` string hosts inject; maintainer-flagged as out of date 2026-09-15, rewritten as WO-3 and verified equal to the reference text, O46a).** Required content, in this order: (1) what the server is — codified US Code by annual edition plus public laws, with `currentthrough` on every text response as the staleness disclosure; (2) that `possibly_superseded` runs automatically on every `get_us_code_section` success — the consumer does not need to run the composition recipe to get the check, because the server has already run exactly that query and echoes it; (3) what each state means for the consumer's next move: `laws_indexed` — a listed law *mentions* the section, read it with `get_public_law` to find out whether the text changed; `none_indexed` — repeating the same query by hand is redundant, and silence is not evidence of currency because of the measured recall gap (O21, O43b), so the only further moves are widening the query (drop the date bound, try `search_public_laws` full text) or reading the source credits in the section itself; `not_checked` — the echoed `query` is the manual retry; (4) the composition recipe, kept, but framed as the widening step rather than the first step. > Search and retrieval over the United States Code and Public Laws as published by GPO on GovInfo. The US Code tools serve the codified law by annual edition (annual editions lag enactment by 18+ months); every text response carries a `currentthrough` date as the staleness disclosure. For law enacted after that date — or law that never enters the Code at all — use the public-law tools.
>
> You do not need to check for later laws yourself: every `get_us_code_section` success already carries `possibly_superseded`, a three-state indicator (`laws_indexed` / `none_indexed` / `not_checked`) computed on every call by querying GovInfo for public laws published after that edition's `currentthrough` and indexed against the section. Read the object's `caveat`.

**Wire shape, noted and accepted (O40).** Responses carry the envelope twice — `structuredContent` (typed; what the Layer-1 checks point at) and its JSON serialization in `content[0].text` (what hosts inject into model context, per the MCP dual-emission convention). Model-context cost is 1×; the duplication is wire/trace-side and accepted. Do not "fix" one copy away: the text copy is host visibility, the structured copy is the instrument.

**Collection scoping (R17, measured by O55; build order WO-8).** Each search tool runs in exactly one collection — `search_us_code` in USCODE, `search_public_laws` in PLAW — and the caller's `query` cannot move it. Corrected 2026-09-20: the contract had said the server prepends its collection "unless the query already contains a `collection:` term", which licensed any collection at all; the served server did exactly that, returning PLAW and BILLS hits from `search_us_code` and a US Code hit under the public-law `recall_caveat` from `search_public_laws` (O55a). The rule: the server finds every collection clause in `query` — the letters `collection`, in any letter case, followed by optional whitespace and a colon, **anywhere in the string**: nothing exempts an occurrence, not double quotes, not parentheses, not whatever characters precede it (`subcollection:` counts). Corrected 2026-09-20 (O57e): the rule as first issued exempted a clause "outside a double-quoted phrase", and WO-8, built faithfully to it, was measured letting `"fair use collection:PLAW` through — one unbalanced quote, 11 USCODE + 7 PLAW hits — because upstream does not treat an unterminated or escaped quote as opening a phrase; the server must not run a quote parser that can disagree with upstream's, so it runs none. The clause's value is everything after the colon up to the next whitespace, closing parenthesis, or end of the query — or, when the value opens with a double quote, through the next double quote, which must itself be followed by whitespace, a closing parenthesis, or the end. A clause conforms only if that whole value is the tool's own collection, bare or double-quoted, in any letter case, written with no whitespace after the colon — `collection:USCODE*`, `collection:USCODE,PLAW` and the like do not conform (O57f: the first build read the value only up to the first non-word character and sent them upstream, where each returned HTTP 500) (`collection:USCODE`, `collection:uscode`, `COLLECTION:"USCODE"` — the spellings upstream was measured to honor, O55b). If every clause conforms, the query goes upstream as the caller wrote it, with the tool's canonical clause prepended only when the query carries none — so the `possibly_superseded` recipe, whose echoed `query` begins `collection:PLAW`, pastes into `search_public_laws` unchanged. If any clause does not conform — another collection, a parenthesized value list, the space-after-colon form, a negated clause, an empty value — the call is refused before any upstream request with `outcome: out_of_scope_collection` (the shape of `out_of_scope_private_law`): the offending clause verbatim, the tool's collection, the tool that serves the named collection when there is one (`collection:PLAW` on `search_us_code` points at `search_public_laws`, and the reverse), and a statement that no search was run — a refusal must not read as zero results. Why refusal and not repair: upstream unions repeated collection terms wherever they sit, `collection:USCODE collection:PLAW` and `collection:USCODE (collection:PLAW …)` both returning the two collections' hits added together (O55c), so prepending the right clause next to a wrong one scopes nothing, and silently deleting the caller's clause would run a query they did not write. Why the space form is refused rather than ignored: upstream does not read `collection: USCODE` as a restriction (O55d), so a caller who writes it believes in a scope that does not exist; the rule is deliberately conservative — a negated foreign clause was measured harmless (O55c) and is refused anyway, because the validator's job is to be obviously right, not to model upstream's grammar. The cost, accepted: a phrase search for the literal text `collection:` — `"the collection: of duties"` — is refused, and the refusal message says to write the phrase without the colon; the one such phrase measured returned zero hits anyway (O57d). Conforming clauses need no operator analysis: upstream lifts collection clauses out of the boolean structure and filters on their union, so `"fair use" AND NOT collection:USCODE` and `"fair use" OR collection:USCODE` both return the in-collection set (O57g) — finding every clause upstream would find is the whole job. Not required: parenthesizing the caller's query. A top-level `OR` was measured not to escape a prepended clause — bare and parenthesized forms returned identical counts, 100 of 100 page hits in-collection (O55e, the preregistered escape falsified). The citation-resolution and detector queries the server builds itself are outside this rule; it binds the `query` argument of the two search tools. `get_us_code_section` and `get_public_law` take no query and are unaffected.

**Resource lifecycle (R19b, from S17 finding 6).** An upstream HTTP client the server creates for itself is closed when the server shuts down, on every transport, through the MCP server's lifespan — not left to interpreter exit. A client handed to the server by whoever constructed it (the tests do this) belongs to them and is never closed by the server. Not observable from outside the process, so its verification is unit-level and says so; that is a limit on the instrument, not on the requirement.

**A cancelled call leaves nothing running (S32 finding 1).** When a tool call ends — by the caller's cancellation, a success, a failure outcome or an exception — every upstream request the server started for it ends with it: the citation search, the text fetch and the speculative staleness query are cancelled if still in flight, and no upstream request is issued on the call's behalf afterwards. This is the staleness rule's "waited for or cancelled and never silently discarded" carried to the case where nobody is waiting: a query that outlives its call spends the key's hourly quota (O13) on a result nothing will read. The protocol lets any host cancel a call, so the case is reachable. Added 2026-09-29 from S32 finding 1, a claim about code backed by a reproduction this session has not seen. Not observable from outside the process, so verified at unit level; that is a limit on the instrument, not on the requirement.

## `get_us_code_section`

Resolve a citation and return the section's text, notes included.

Arguments: `citation` (string — accepts "17 U.S.C. 107", "17 USC 107", "17 U.S.C. § 107(b)", "42 U.S.C. 2210 note", or equivalently `title` + `section` as separate fields), optional `year` (edition year), optional `max_chars`/`start_char`. Optional `granule_id` (R16): a USCODE granule id exactly as a disambiguation list or `search_us_code` result carried it, with optional `package_id` alongside; when present it selects the granule directly and the citation search is skipped — `citation` may still be supplied with it, and is then used for the staleness detector (below); `year` is ignored with a warning in the response, since the id names its edition.

Behavior: normalize per `30-search.md` — mandatory strips: parenthetical subsection (O11) and trailing "note" (O16); when either strip fires, the response says so and names the containing section it resolved instead. Search `collection:USCODE citation:"…"` with `historical` set iff `year` given; on multiple hits after year filtering, return the disambiguation list (ids + titles) rather than guessing — and the list must carry the true total of candidates alongside however many fit the page, with any capping stated, so 100 shown of 251 (the measured bare-appendix case, O24) never reads as 100 of 100 — the true total is upstream's `count` when no `year` was given, and the count after the year filter when it was (O93c: upstream's 78 across every edition since 1997 is not the total of the two 2024 candidates the filter kept; corrected by WO-17 C, which also discloses upstream's unfiltered figure as `count_all_editions`); fetch the winning granule's `txtLink` and, concurrently, run the `possibly_superseded` detector query (cross-cutting contract above); return text + provenance + the three-state staleness indicator. A citation that resolves to zero granules reports the normalized citation and the raw query so the caller can retry with `search_us_code`. The disambiguation message names the actual re-request path: `granule_id` from the list (R16), or `year` when the candidates differ by edition — never an input the tool does not accept (the pre-R16 wording "by ids" promised one, O45c).

By-id behavior (R16, WO-3): with `granule_id`, the server does not construct any URL from the id. It fetches the granule summary — `GET /packages/{package_id}/granules/{granule_id}/summary`, the endpoint measured in O9 — and takes `txtLink` from it verbatim (the links-verbatim rule, O4). `package_id` comes from the argument when given; otherwise from the id's leading `USCODE-{year}-title{n}` segments, which is the one piece of id structure this spec relies on (measured shape, O9/O14) and is disclosed as `package_id_derived: true` in the response. Provenance, `currentthrough`, windowing, `find`, `structure`, and the banner are identical to the citation path — the payload is the same `/htm` document. Outcomes (measured O46c, ratifying the implementation's correction of this spec's earlier "404"): the summary endpoint answers **400 `invalid granuleId`** for any nonexistent granule under a real package (wrong section, wrong chapter, wrong edition, wrong title, garbage — 6 of 6 shapes) and **404** only for a nonexistent package (2 of 2); both are `not_found`, distinguished by `not_found_kind: granule | package`, with the upstream status and body echoed and the id named; any other 400, and every 5xx, stays `upstream_error`, and 429 stays rate-limited — a failure never reads as "not found". A non-USCODE id is rejected as `invalid_argument` before any call. The accepted id grammar is `USCODE-{year}-title{n}` followed by at least one hyphen-separated segment of letters and digits, in which a dot or an underscore may appear inside the segment but never lead it and never repeat — `(-[A-Za-z0-9]+(?:[._][A-Za-z0-9]+)*)+` — matched exactly as given — a character class, not a parse (the spec still relies on the leading segments alone, O14). Ratified from WO-29 A (O118c): a dot or underscore between a letter and a digit is inside a segment, so `…-rule.1` passes the class and is answered by upstream as `not_found`; the class does not know where a segment's letters end. Amended 2026-09-29 (F21, O116; build order WO-29 A): O86b's 540 ids had no dot or underscore, but the corpus does — 52 of 19,947 ids across eight 2024 titles, dotted appendix rules (`…-dup1-rule4.1`) and second sections of a number (`…-sec1932_2`) — and the server hands those ids out in search results and candidate lists while the narrower grammar refused them ("is not a USCODE granule id; nothing was fetched"), so an id the server served could not be re-entered. Anything else — a slash, a leading or doubled dot, `..`, a query character or whitespace included — is `invalid_argument` naming the id, before any request; the `/../` case S26 found stays refused (S26 finding 2: an id carrying `/../` reached the summary URL and its 404 read as "no package"; WO-15 B). Staleness detector on the id path: it needs a `{title} U.S.C. {section}` form, and the granule summary's `usCodeCitation` was measured null (O9), so the detector runs on the supplied `citation` after the usual strips when one is given, and otherwise reports `not_checked` with `reason: no_citation_for_detector` and a message saying to pass `citation` alongside `granule_id` to get the check. **The supplied citation is the caller's word, and the response says so (O61d, from S17 finding 2).** Served at 633e61c, the title 17 § 107 granule with `citation: "42 U.S.C. 2210"` came back `success` with title 17's text, `normalized_citation: 42 U.S.C. 2210`, a `laws_indexed` staleness result for the title 42 section, and no warning. ## `search_us_code`

Full-text and fielded search over the USCODE collection — the discovery path for topics, appendix material (O19), and anything citation resolution redirects here.

Arguments: `query` (govinfo query syntax; the server prepends `collection:USCODE` when the query carries no collection clause; a clause naming USCODE is accepted, any other collection clause is refused with `out_of_scope_collection` before any upstream request — "Collection scoping" above, R17), optional `page_size` (default 20, max 100), `offset_mark` (default `*`), `historical` (default false).

Returns: `count`, next `offset_mark`, and per hit: `title`, `packageId`, `granuleId`, `dateIssued`, download links. It returns pointers, not text — the caller follows up with `get_us_code_section` (or the ids directly).

**Result order (O109; build order WO-24).** Every upstream search request this tool and `search_public_laws` send carries `sorts: [{"field": "score", "sortOrder": "DESC"}]`. Without it upstream orders hits string-descending by granule id (O109c), so a page of a 134-hit result is a page of title 7 sections and the one heading match is on page 4 — the served order behind the S31 field miss, where a capable consumer read the first page, found nothing, and answered from the wrong provision. `count`, `offset_mark` and page membership are unchanged by the sort; the server never re-ranks, filters or merges hits itself. The description says, character for character: "Results are relevance-ordered. Unquoted terms are all required, so start with the asker's own topical words, unquoted; double quotes match an exact phrase; `title:` searches section headings (e.g. `title:collateral usctitlenum:12`)." Served from WO-24 (O111) with the clause before it ended by a full stop and the one after capitalized: "…`shorttitle:...`). Results are relevance-ordered. … The `historical` ARGUMENT …". The three facts a consumer needs are measured (O109b, O109d), and the first query to send is the asker's words because under score order they put the heading match first (O109c). `search_public_laws` carries the same sort for one behavior; its default order is the same string-descending id order (O111a). Under the sort a hit can be served twice across a page boundary, about one walk in three, and none is lost (E39, O112); the server does not deduplicate across pages, since it holds no state between calls, and the description says nothing of it unless a consumer is measured misled. The queries the server builds itself (citation resolution, the `possibly_superseded` detector) select by citation and are outside this rule.

**A page past the end is not zero results (F19, O111e; build order WO-27).** When `search_us_code` or `search_public_laws` is called with a continuation `offset_mark` — anything but "*" — and upstream returns no hits, the envelope stays `success` with `results` empty and `count` as upstream sends it, and its message says, character for character: "No more results: this continuation page is past the end of the result set. The search itself succeeded; 'count' on this page is upstream's value for a page past the end, not the size of the result set, which the first page reported." The zero-results message is served on a first page only, where it is true.
