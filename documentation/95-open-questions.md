## Preregistered experiments — pending

E15 (preregistered 2026-09-02, maintainer-approved; from O40b and F3). **Question:** how many copies of a large tool result enter the consumer's request context, and does a 100,000-char default window get delivered inline at all? These are one measurement because one capture answers both. **Why it can't be settled otherwise:** `api-surface.jsonl` records `path`, `model`, `tool_names` and `body_keys` per request but never message bodies, so no artifact in a run says what reached the model; and a consumer's own report of its context is not evidence (S10 — the instrument reporting on itself). **Instrument (harness-side, mcp-e2e):** extend the api-surface capture with per-request body size and, where the driver already calls `/v1/messages/count_tokens` (observed at seq 3 in isolation/C/C1), the returned count — keys only, never bodies, so nothing new is published into artifacts. Run C1 in at least the floor and isolation cells. **Expected:** request context grows by ~1x the serialized envelope per tool result (~26k tokens for a 100k window), matching O40's accepted reading. **Falsifier:** growth of ~2x the envelope — then the duplication costs model context as well as wire, O40's acceptance is void, and the response shape gets reopened. **Second reading, from the same capture:** if the 208KB result never appears in a request body at full size, the F3 retreat is a host inline-delivery limit and the default `max_chars` is above it; if it appears in full, the retreat was consumer preference and F3 is a tuning question, not a threshold one. **Pre-committed dispositions,** so the result picks rather than reopens a debate: 2x context → response-shape work (the summary-plus-pointer option F1 parked); host limit confirmed → lower the default to below the measured threshold and say why in the contract; consumer preference → leave the default and close F3 as no-change.
